## Objetivo

Ao fim desta versão o MVP está pronto para entregar: uma run inteira é jogada pela interface com os três clãs num teste automático, nenhum erro inesperado prende o jogador, o simulador protege o balanceamento contra regressão com faixas por build, os documentos são conferidos contra o código por `npm run docs:check`, e o jogo abre com `npm install && npm run dev` ou como site estático gerado por `npm run build`.

## Passo a passo

### Passo 1 — A run completa pela interface, com os três clãs

**O quê**: `tests/ui/e2e.test.ts` monta o `App` de verdade (com todas as telas de `SCREENS`) sobre um `GameStore` com armazenamento em memória e joga uma run inteira. O começo é pela tela: clica em "Modo História", digita o nome, clica no clã, confere se a afinidade está travada (só no Uchiha), escolhe o preset e clica em "Começar a Saga da Onda". Depois, a função `autoplay` usa os **mesmos comandos** que as telas usam (`rest`, `act`, `chooseReward`, `allocate`, `buy`, `fight`, `continueFromResult`, `resolveSwap`), com as ações de batalha escolhidas por `botAction`, o robô do simulador. O teste exige que a run termine na tela de fim de run, com uma entrada no Histórico, sem `fatalError` e sem nenhum aviso "Erro inesperado". O segundo grupo de casos usa `scenario(strong, ...)`, que dá 40 em todos os atributos base, e exige **vitória** com cada clã, com o título `demonio_da_nevoa` conquistado.

**Por quê**: a spec §13 define o critério de pronto do MVP como uma run completa jogável. Testar cada tela isolada (Beta 0.9.1) não prova que elas se encadeiam: uma tela de resultado que não deixa continuar, ou um mapa que não aparece depois de um Acampamento, passaria nos testes de unidade. Como o `App` está montado, **toda tela é desenhada a cada passo**: um erro de render em qualquer tela, em qualquer momento da run, derruba o teste. Os casos com `strong` existem porque uma run normal pode perder para Zabuza (é um roguelike: perder faz parte), e o teste precisa provar que o caminho da vitória também funciona, até o fim da saga, nos três clãs.

**Alternativas**: um teste de navegador real (Playwright, Cypress) cobriria também o Phaser e o CSS, mas exige baixar navegadores, é mais lento e mais frágil; a interface em DOM com happy-dom cobre a lógica das telas em segundos. Jogar pelo motor direto (como o simulador) seria mais rápido, mas pularia as telas, que é justamente o que se quer provar. Fixar a semente para garantir a vitória numa run normal, sem `strong`, deixaria o teste dependente do balanceamento: qualquer calibração quebraria o teste sem haver bug.

**Riscos e armadilhas**: a primeira versão (`0b6fbee`) liberava a trava de animação dentro do `autoplay` (`if (s.locked) store.animationsDone()`), sem precisar, e só provava a vitória com um clã. O `5aa63f0` tirou a linha (no teste não há animador inscrito, então nada trava), passou a conferir que o clã e a afinidade escolhidos na tela chegaram ao personagem e provou a vitória com os três clãs. Uma armadilha de teste de ponta a ponta é o laço infinito: `autoplay` tem um limite de 6000 passos, e cada caso tem 120 s de tempo máximo, para um bug que impeça a run de terminar falhar o teste em vez de travar a suíte.

### Passo 2 — Erro inesperado nunca prende o jogador

**O quê**: o `GameStore` ganhou `fail(message)`, que vai para a tela de erro, guarda a mensagem em `fatalError`, solta a trava (`locked: false`) e descarta a navegação adiada; um sinal `failing` impede que `fail` chame a si mesmo em laço. O método privado `set` passou a chamar cada ouvinte dentro de `try/catch`: se um ouvinte lança, o store chama `fail`. `App.render` envolve o desenho da tela num `try/catch`: fora da tela de erro, chama `store.fail(msg)`; se a própria tela de erro lançar, desenha um painel mínimo com "Algo deu errado" e "Recarregar o jogo", sem depender de nenhuma tela. Um animador que lança vira aviso e o store chama `animationsDone()` na hora. `navBlocked()` faz `go`, `back` e `toMenu` serem ignorados durante a animação da batalha, e `toMenu` zera a fila de troca de jutsu. Na leitura do save, entradas do Histórico que não são objetos são descartadas. Tudo isso é do `bec6a2e`. Depois, o `597df55` impediu que a tela de batalha sobrescrevesse a tela de erro.

**Por quê**: num jogo com save automático, um erro que trava a tela é pior que um erro que mostra uma mensagem: o jogador não sabe se perdeu a run e não tem botão para sair. A spec §12 ("Robustez") pede que o jogo nunca fique preso. A tela de erro com "Recarregar o jogo" resolve o caso comum, porque o save da run está gravado e o recarregamento volta ao último estado bom.

**Alternativas**: um `window.onerror` global pegaria todo erro, mas sem saber em que estado o store ficou (travado ou não). Deixar o erro estourar e confiar que o jogador recarregue a página funciona para quem conhece o DevTools, mas um jogador comum veria só uma tela congelada. Validar todas as entradas em todas as funções evitaria parte dos erros, mas não os bugs que ninguém previu.

**Riscos e armadilhas**: a revisão final do Plano 2 achou que um render que lança deixava o jogo travado para sempre. O caminho era este: `step` chama `set({ ..., locked: true })`, o ouvinte do `App` redesenha, a tela de batalha lança, a exceção sobe por `set` e os animadores nunca são chamados. Sem animação, ninguém chama `animationsDone()`, e `locked: true` recusa todo comando dali em diante. O `bec6a2e` fechou esse caminho, com o teste `tela que lança vira a ErrorScreen e o jogo não fica travado`. A Task 3 do Plano 3 achou um segundo caso: um render que quebra **fora** da batalha (no mapa, ao clicar em "Lutar") ia para a tela de erro, mas a linha seguinte de `step` trocava para a tela de batalha e a mensagem sumia. O `597df55` criou `isError()` e verifica o erro antes e depois de trocar de tela (teste `render que quebra fora da batalha: a ErrorScreen não é sobrescrita pela tela de batalha`). O método existe à parte porque o TypeScript **estreita** o tipo de `this.s.screen` depois de um `if`, e acharia impossível a tela ser `'error'` logo depois de ter sido outra coisa, sem saber que `set()` a mudou no meio.

### Passo 3 — Faixas de regressão por build

**O quê**: o simulador da Alfa 0.8 joga milhares de runs com oito builds (combinações de estilo e clã) e mede métricas como "vence Zabuza" e "HP no fim dos encontros comuns". As metas de design da spec §12 estão em `TARGETS`, em `src/game/sim/report.ts`. O `68d6179` acrescentou `BUILD_BANDS`: para cada build que mede fora da meta, uma faixa própria, nunca mais estreita que a meta (Ninjutsu / Uchiha vence Zabuza em 40–75% em vez de 45–75%; Ninjutsu / Uzumaki vence Haku, dado que venceu Zabuza, em 70–97% em vez de 70–85%). `bandFor(build, métrica)` devolve a faixa da build ou, sem uma, a meta. `checkTargets` usa as faixas e faz `npm run sim:check` falhar quando uma build sai da **sua** faixa; `designGaps` lista, só como informação, a distância de cada build até a meta de design, e `tools/simulate.ts` a imprime. Nenhum número de `src/game/Balance.ts` mudou.

**Por quê**: um **teste de regressão** existe para avisar quando algo que funcionava piorou. Depois de quatro iterações de calibração (registradas em `docs/balance-log.md`), oito metas continuavam fora por uma razão estrutural: a distância entre a build mais fraca contra chefes (Uchiha) e a mais resistente (Uzumaki) é maior que a largura das faixas da spec, e os botões de calibração mexem em todas as builds juntas. Por exemplo, o HP do Haku (grau B) foi para ×1,7 <!-- fact: BALANCE.enemyGrades.B.hpMult=1.7 --> na calibração, e endurecer o Haku ainda mais derruba o Uchiha abaixo da meta antes de baixar o Uzumaki até ela. Com o `sim:check` sempre vermelho, ele parava de proteger contra qualquer coisa. Com faixas por build, o check fica verde no estado atual e volta a ficar vermelho se uma mudança futura piorar alguma build.

**Alternativas**: mexer no design do jogo (tirar os kits de cura da escolha 1-de-3, reduzir a cura do kit, rever a passiva do Uzumaki) fecharia a distância de verdade, mas é decisão de design, não de calibração, e foi adiada para depois de o usuário jogar. Alargar as metas de design para todas as builds esconderia o problema. Desligar o `sim:check` tiraria a única proteção automática do balanceamento. A escolha das faixas por build foi do usuário, registrada em `docs/balance-log.md`.

**Riscos e armadilhas**: o perigo de uma faixa por build é virar um lugar para esconder regressão. Por isso `tests/sim-bands.test.ts` prova que nenhuma faixa é mais estreita que a meta, que toda chave de `BUILD_BANDS` é uma build do simulador, que um valor um ponto acima do teto de uma faixa ampliada falha e que um valor dentro da faixa da build continua aparecendo como distância da meta. E o que isso **não** resolve precisa ficar dito: o jogo continua mais fácil para Uzumaki (Haku quase sempre cai) e no limite para Uchiha. Com 3000 runs, Ninjutsu / Uchiha vence Zabuza em 41%, a um ponto do piso da sua faixa; uma mudança pequena que endureça os chefes pode tirá-lo dela primeiro.

### Passo 4 — Documentos verificáveis

**O quê**: `npm run docs:check` roda `tools/docs-check.ts`, que lê a lista de documentos de `tools/docs-specs.ts` e confere cada um com as funções puras de `tools/docs-lib.ts`. Para cada documento, ele confere que os títulos obrigatórios existem, que todo caminho de arquivo citado entre crases existe no repositório, que não há marcadores de pendência e que cada número marcado com um comentário de fato (o caminho de uma chave do `BALANCE` e o valor esperado) é igual ao valor em `src/game/Balance.ts`. Para as versões do curso, `checkCourse` exige no mínimo três `### Passo`, cada um com os quatro rótulos (**O quê**, **Por quê**, **Alternativas**, **Riscos e armadilhas**), e o patch log completo. O `62aad39` corrigiu o verificador: "todo" e "toda" em português eram confundidos com o marcador de pendência em inglês, e agora só as maiúsculas contam.

**Por quê**: documento desatualizado é pior que nenhum, porque o leitor confia nele. Um curso que cita um arquivo renomeado, ou um documento de design que diz que o Haku tem HP ×1,5 quando o código tem ×1,7, ensina errado. Amarrar os números ao `BALANCE` faz uma calibração futura derrubar o `docs:check` até alguém atualizar o texto.

**Alternativas**: gerar a documentação a partir do código (como TypeDoc) garante a precisão, mas só descreve a API; não explica o porquê, as alternativas nem as armadilhas. Revisão manual a cada mudança depende de alguém lembrar. Testar os exemplos do documento (como os doctests do Python) exigiria que os documentos tivessem código executável, o que não é o caso de um curso narrativo.

**Riscos e armadilhas**: o verificador confere a forma, não o conteúdo: uma frase errada sem número marcado e sem caminho passa. Por isso a regra de escrita é ler o código antes de afirmar, e por isso as tasks dos documentos registraram onde o plano e o código divergiam (vale o código). A primeira versão do verificador também tinha uma armadilha de idioma: a busca por marcadores ignorava maiúsculas e minúsculas, e o português usa "todo" em quase todo parágrafo; a correção (`62aad39`) diferencia caixa só para os marcadores em inglês e mantém as frases de pendência em português sem diferenciar caixa. Um cuidado prático: o verificador lê os comentários de fato em qualquer lugar do texto, inclusive dentro de crases; para descrever o formato em prosa, escreva-o em palavras.

### Passo 5 — Entrega

**O quê**: com Node 22 (o `package.json` exige `node >= 22` em `engines`), `npm install && npm run dev` abre o jogo no servidor de desenvolvimento do Vite. `npm run build` roda `tsc --noEmit` e `vite build` e gera a pasta `dist/` estática; com `base: './'` no `vite.config.ts`, ela abre de qualquer pasta ou servidor de arquivos, sem backend. Antes de entregar, cinco comandos têm de passar: `npm run build`, `npm test`, `npm run sim:check`, `npm run docs:check` e o próprio `npm run dev` abrindo o menu. O `ced92e8` atualizou `happy-dom` (15 para 21.0.1) e `vitest` (3 para 5.0.4) por alertas de segurança do `npm audit`; as duas são só dependências de desenvolvimento, e a suíte e o build passaram depois do upgrade.

**Por quê**: o jogo é 100% local no navegador (spec §1): sem servidor, o save fica no `localStorage`, e qualquer hospedagem de arquivos estáticos serve. Um único conjunto de comandos verdes é o contrato de entrega: o motor (`npm test`), o balanceamento (`npm run sim:check`), os documentos (`npm run docs:check`) e o build (`npm run build`).

**Alternativas**: empacotar como aplicativo de desktop (Electron, Tauri) daria um ícone e acesso ao disco, mas multiplicaria o tamanho e exigiria build por sistema operacional. Publicar só o código-fonte, sem `dist/`, obrigaria quem quer jogar a instalar Node.

**Riscos e armadilhas**: um upgrade de dependência de teste pode quebrar a suíte sem aviso, principalmente o simulador de DOM: o `happy-dom` subiu seis versões de uma vez (Review Focus 3 do Plano 3). A regra foi rodar `npm test` e `npm run build` logo depois do upgrade, antes de qualquer outra mudança, para isolar a causa se algo quebrasse. O `npm run sim:check` leva de 33 a 45 s (1000 runs por build) e o relatório completo `npm run sim` (3000 runs) cerca de 141 s, então não dá para rodá-los a cada mudança: eles são o último passo antes de entregar.

## Critérios de conclusão

- `npm run build` termina sem erros e gera `dist/`.
- `npm test` passa (motor e interface, incluindo `tests/ui/e2e.test.ts` e `tests/ui/robustness.test.ts`).
- `npm run sim:check` termina com "Nenhuma build saiu da sua faixa de regressão."
- `npm run docs:check` termina com "Documentos conferidos: 14."
- `npm install && npm run dev` abre o menu do jogo no navegador.

## Testes

- `tests/ui/e2e.test.ts`: prova a run completa pela interface com Uchiha, Uzumaki e Sem clã (criação pela tela, run até o fim, Histórico gravado, nenhum erro inesperado) e a vitória com uma build forte de cada clã.
- `tests/ui/robustness.test.ts`: prova que uma tela que lança vira a tela de erro sem trava, que a tela de erro não é sobrescrita pela batalha, que uma tela de erro que também lança não derruba o `App`, que um animador que lança solta a trava e aplica a navegação adiada, que o Histórico com entradas inválidas abre e registra o fim de run, que `go`/`back`/`toMenu` são ignorados com a batalha travada e que o boot refinaliza uma vitória cuja meta falhou.
- `tests/sim-bands.test.ts`: prova as faixas por build (nunca mais estreitas que a meta, valor fora da faixa falha, builds não focadas fora do check).
- `tests/docs-check.test.ts`: prova o verificador (títulos fora de blocos de código, caminhos em crase, marcadores de pendência, fatos contra o código, estrutura do curso).
- `tests/ui/log.test.ts`: prova o singular "1 turno" (`597df55`).
